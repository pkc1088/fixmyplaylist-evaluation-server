### 배경

- 참고 사례 초기 적재는 CSV 파일을 읽어 Cloud SQL MySQL의 `reference_cases`에 저장한 뒤 Gemini 임베딩 생성과 Qdrant 색인을 순차 실행한다.
- MySQL 저장 이후 외부 네트워크 장애나 API 오류로 Qdrant 색인이 중단되면 원본 저장소와 벡터 색인 사이에 불일치가 남는다.
- 초기 적재는 최초 구축이나 일괄 데이터 반영 시 관리자가 직접 실행하는 드문 작업이므로, 부분 실패 복구에 어느 수준의 정합성 메커니즘을 둘지 결정해야 했다.


### 결정

- 초기 적재 경로에는 Outbox 테이블이나 별도의 분산 보상 트랜잭션을 두지 않는다.
- 적재 중 부분 실패가 발생하면 관리자가 동일한 `POST /api/admin/rag/setup/initial` 엔드포인트를 다시 호출하거나 `POST /api/admin/rag/setup/reindex`를 실행해 정합성을 맞춘다.


### 검토한 대안

- 초기 적재에 Outbox 패턴과 비동기 릴레이 적용: 최초 구축 시 한 번 또는 매우 드물게 실행하는 작업에 Outbox 적재, 재처리 스케줄러, 상태 추적 복잡도를 결합하는 것은 운영 빈도 대비 구현 및 유지보수 비용이 과도해 기각했다.
- 실패 시 MySQL 저장분을 되돌리는 보상 트랜잭션 구현: MySQL과 Qdrant는 분산 트랜잭션을 지원하지 않으며, 롤백 로직 자체가 실패할 때의 예외 분기까지 관리해야 하므로 멱등 재실행보다 장애 지점이 늘어나 기각했다.


### 결과 및 제약

- 초기 적재와 재색인은 몇 번을 반복 실행해도 동일한 결과를 내도록 반드시 멱등하게 유지해야 한다. MySQL에서는 동일 ID 레코드를 CSV 값으로 덮어쓰며, Qdrant 포인트 ID는 `referenceCaseId`에서 유도한 결정적 UUID를 사용해야 한다.
- Qdrant 포인트 ID를 무작위 UUID로 생성하는 방식은 사용할 수 없다.
- 초기 적재 중 부분 실패가 발생해도 시스템이 자동으로 복구하지 못한다. 관리자가 응답 본문과 로그를 확인해 수동으로 재호출해야 한다.
- CSV에서 누락된 기존 행은 삭제하지 않으므로 초기 적재 재호출만으로 기존 참고 사례를 일괄 제거할 수 없다.
