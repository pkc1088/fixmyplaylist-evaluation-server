### 배경

- AI 평가 실행 중 외부 API 오류나 응답 파싱 실패가 발생하면 `EvaluationCase`는 `FAILED` 상태로 기록되고 다음 실행에서 재시도된다.
- 누적 3회 실패한 건은 `DEAD` 상태로 전이한다.
- 일일 평가 규모가 100건 이하인 환경에서 `DEAD`로 전이된 건을 시스템 API로 다시 `PENDING`이나 `FAILED`로 되돌려 자동 재평가할 수 있게 할지 결정해야 했다.


### 결정

- `DEAD` 상태는 자동 평가 대상에서 영구 제외하고 개발자가 직접 검수한다.
- `DEAD`에서 `PENDING`이나 `FAILED`로 되돌리는 상태 역전이 로직과 재평가 엔드포인트는 구현하지 않는다.


### 검토한 대안

- 관리자용 `DEAD` 상태 초기화 및 재평가 API 제공: 일 100건 이하 규모에서 3회 연속 실패하는 건수는 극소수이며 입력 데이터나 파싱 경계 문제일 가능성이 크다. 재시도 횟수 초기화 규칙과 무한 루프 방지 로직을 추가하고 유지하는 비용이 사람이 직접 검수하는 비용보다 커 기각했다.
- 실패 횟수 상한 없이 매 실행마다 무기한 재시도: 영구적으로 실패하는 건이 매 배치마다 Gemini API 호출 비용을 소모하고 에러 로그를 반복 누적시켜 기각했다.


### 결과 및 제약

- 외부 서비스 장기 장애로 여러 건이 3회 연속 실패해 `DEAD`로 전이되더라도 애플리케이션 API만으로 일괄 재평가를 실행할 수 없다. 이 경우 개발자가 직접 검수하거나 운영 DB에 수동 개입해야 한다.
- 상태 기계에서 `DEAD`는 자동 평가 흐름의 종단 상태로 고정되며, 어떤 코드 경로에서도 `DEAD` 건을 자동 평가 조회 대상에 포함하지 않는다.
