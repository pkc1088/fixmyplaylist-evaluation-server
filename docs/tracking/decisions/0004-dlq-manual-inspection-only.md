### 배경

- Kafka 입력 토픽에서 수동 풀링한 복구 완료 이벤트가 JSON 역직렬화 실패, `eventId` 100자 초과, 제목 공백, 또는 Cloud SQL 일시 장애로 저장에 실패하면 원문 그대로 DLQ 토픽으로 발행된다.
- Cloud Run min-instance 0과 일 1회 배치 실행 환경에서 DLQ 토픽의 메시지를 자동 재소비해 재처리하는 파이프라인을 둘지 결정해야 했다.


### 결정

- DLQ 토픽은 실패 메시지 격리와 기록 용도로만 사용한다.
- 이 서비스 내부에 DLQ 자동 컨슈머나 자동 재처리 로직을 구현하지 않는다. 운영자가 로그와 DLQ 원문을 확인해 원인을 조치한 뒤 필요한 건만 수동으로 원본 토픽에 재발행한다.


### 검토한 대안

- 별도 DLQ 자동 재소비 스케줄러 및 재시도 파이프라인 구축: min-instance 0 환경에서 DLQ 전용 트리거, 재시도 횟수 추적 헤더, 최종 폐기 경로를 추가로 관리해야 한다. 스키마 불일치나 공백 제목 같은 영구 결함 메시지는 자동 재시도로 해결되지 않아 구조 복잡도만 증가하므로 기각했다.
- 저장 실패 시 DLQ로 보내지 않고 오프셋 커밋 보류 후 재폴링: 특정 결함 메시지 한 건 때문에 파티션 소비가 막히거나 동일 실패가 매 실행마다 반복되어 정상 이벤트 적재를 방해하므로 기각했다.


### 결과 및 제약

- Cloud SQL 일시 장애처럼 인프라가 회복되면 정상 처리될 수 있는 이벤트도 DLQ로 이동한 뒤에는 자동 복구되지 않는다. 운영자가 수동으로 확인하고 재발행해야 한다.
- DLQ 토픽 발행 자체마저 실패하면 별도 우회 큐가 없으므로 에러 로그에 기록된 이벤트 원문에 의존해 복구해야 한다.
- 이 서비스의 Kafka 연동 범위는 입력 토픽 읽기와 DLQ 토픽 쓰기로 고정되며 DLQ 토픽을 읽는 컨슈머는 구현하지 않는다.
