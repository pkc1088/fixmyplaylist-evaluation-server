# 엔지니어링 노트

코드만 봐서는 이유를 알기 어려운 설계 선택, 알려진 한계, "이상해 보이지만 의도된 것"을 적는다.

## 설계 선택
- **Kafka를 수동 폴링한다(`@KafkaListener` 미사용).** Cloud Run이 min-instances=0인 서버리스라 상시 리스너를 둘 수 없다. 평가 호출이 올 때마다 컨슈머를 만들어 읽고 닫는다.
- **수신과 평가가 분리되어 있지 않다.** 한 번의 호출이 신규 수신과 밀린 건 평가를 모두 하므로, 이전에 실패한 건도 다음 호출에서 처리된다.
- **중복 이벤트 방지는 DB 기본 키 충돌에 기댄다.** 그래서 `saveToInboxIdempotent`는 트랜잭션 밖에서 호출한다. 바깥 트랜잭션이 있으면 키 충돌 예외가 그 트랜잭션을 롤백 전용으로 만든다.
- **엔티티가 `Persistable`이다.** 기본 키를 애플리케이션이 정하는 엔티티에서 불필요한 조회·병합을 피하고 배치 쓰기를 쓰기 위해서다. 그래서 삽입(`save`)과 갱신(`update`)을 나눠 쓴다.
- **Qdrant 점 ID가 `referenceCaseId`에서 만든 결정적 UUID다.** 재색인·재적재해도 같은 사례가 덮어쓰이고 중복되지 않는다. 초기 적재의 "재호출로 복구" 방식이 이 성질에 기댄다.
- **이벤트는 모르는 필드를 무시한다.** 발행 쪽이 필드를 추가해도 이 서비스가 깨지지 않는다. 필드를 프롬프트·임베딩에 넣으면 외부 전송 범위가 달라진다(`docs/security.md`).

## 이렇게 보이지만 의도된 것
- **초기 적재에 부분 실패 보호(Outbox)가 없다.** 수동으로 트리거하는 작업이라 실패하면 같은 엔드포인트를 다시 호출해 맞추면 된다는 판단이다(`docs/tracking/decisions/0001-*`).
- **평가 호출에 건수 상한과 타임아웃 대비가 없다.** 관리자가 수동으로 트리거하는 작업이라 응답 시간을 신경 쓰지 않는다.
- **`DEAD` 재평가 기능, DLQ 소비 코드, 자동 승인이 없다.** 모두 의도적이다(`docs/tracking/decisions/0003-*`, `0004-*`, `docs/business-rules.md`).
- **PoC 수치는 변경 판단의 기준이 아니다.** 프롬프트·모델·`RAG_TOP_K`를 바꿀 때 PoC 결과를 맞추지 않는다. 변경은 사용자가 지시했을 때만 한다.

## 알려진 한계
- 승격은 미구현이다. `ReferenceCasePromotionService` 초안은 Outbox가 없고 삽입을 강제해서 재승격 시 키 충돌이 난다. 정식 구현은 Outbox와 재처리로 한다(`docs/tracking/decisions/0002-*`).
- 검수 대기 조회와 승격 엔드포인트는 호출 경로가 없다. 검수 메뉴를 만들 때 연결한다.
- 유사 사례 검색에는 유사도 하한이 없다.
- 나머지 불일치와 이슈는 `docs/tracking/findings.md`에 있다.
